# Authorized chat attachments

A message may include one file and an optional text caption. The composer supports selection/removal, validation feedback, sending/retry, and authenticated download. PNG/JPEG files also offer View image and Hide image in the message; Download file remains a separate action. Viewing fetches authorized bytes without saving a file to disk. English is the default; Russian guidance is available. Existing message deletion removes attachment access too, including moderator deletion.

## Storage and limits

The API supports nonempty UTF-8 `.txt`, `.png`, `.jpg`/`.jpeg`, and `.pdf` uploads up to 5 MiB. It checks the extension and basic file signature (or strict UTF-8 text/control characters), not the entire format or malware. Original names are limited to 120 characters without paths/control characters; only a generated GUID is used on disk. There are no executables, archives, HTML, SVG, arbitrary MIME types or multi-file batches.

The browser previews only PNG/JPEG signatures with dimensions at most 8192 per side and 32 million pixels. It creates a typed raster blob URL after the authorized fetch; direct server downloads remain forced attachments. Preview failures leave Download file available. PDFs/text have download only. Hide, message removal, channel navigation and access/session unmount revoke the preview URL; unmount also cancels pending requests. A new view/download rechecks server access. Already fetched bytes cannot be recalled, and header bounds are not complete format validation or malware scanning.

Files remain outside `wwwroot`. Development defaults to ignored `.local/files`; set `Files__RootPath` to an absolute dedicated persistent directory for other environments. The API process needs read/write permissions, not execute permissions. No public static file mapping is configured. Production Compose mounts `/opt/dosvyazi/data/files` at `/var/lib/dosvyazi/files`; create it with API UID/GID 1654:1654 and mode 700 before an authorized deployment. Existing servers need this directory and the additive migration before updating the API. This documentation does not perform a deployment.

The default stored-blob quota is 512 MiB, configurable through `Files__QuotaBytes`; it includes retained orphan files. Uploads across communities share a PostgreSQL advisory lock for quota checks/file creation. At most two uploads are admitted concurrently per API process before multipart model binding, with no queue; additional requests return 429 and `Retry-After: 2`. Multipart/request bodies are capped at 6 MiB, including overhead. Current limits are engineering defaults, not a measured capacity claim. The filesystem volume must be shared consistently if an operator later runs multiple API instances; such scaling is not introduced here.

## Contract and authorization

All routes start with `/api/v1/communities/{community}/channels/{channel}`:

- `POST /attachments`: multipart `clientMessageId`, `file`, optional `content`; returns 201 with the message and attachment metadata. Cookie authentication, same-origin/CSRF protection, current membership, ViewChannel and SendMessage apply.
- `GET /attachments/{id}`: rechecks current membership and ViewChannel plus attachment/message/channel identity and deletion state. Returns a forced `application/octet-stream` attachment download with `no-store`, `nosniff` and a sandbox policy. No reusable public URL or signed bearer access is issued.

Names and IDs do not grant access. Private-channel denial, nonmembership, ban, leave, deletion and cross-channel references return 404. A visible read-only channel permits downloads but rejects uploads with 403. Validation uses 422, oversized/empty files 413, reused IDs with changed content/file/name 409, unavailable storage 503, and full storage 409. Anonymous API requests return 401; missing CSRF returns 400. The client retains the selected file and request ID after an uncertain send, so retry does not publish a duplicate. File-only messages are allowed; ordinary text-only sends retain their existing behavior.

Metadata, message sequence and outbox entry commit in one database transaction. History/catch-up include attachment metadata; caption edits preserve the blob. Files are written before the metadata transaction commits. An abrupt process exit, write failure or uncertain database acknowledgement can leave a private orphan: it counts against quota and remains for operator review. No automatic orphan deletion risks removing a committed file. These leftover files require a separate, reviewed maintenance procedure; there is no automatic orphan collector in this milestone.

Message deletion immediately denies new download requests. A background task retries physical deletion of known deleted-message blobs every 30 seconds in batches of 100 and records completion. `Files__WorkerEnabled=false` disables it for isolated fixtures; failed cleanup is retried after restart. Already downloaded bytes or a transfer authorized before a permission change cannot be recalled. Back up PostgreSQL and the private file directory together, retaining Data Protection keys separately. A missing blob is a storage failure, not silently an empty download.

This milestone supplies bounded authenticated downloads for a controlled test installation. Signature validation does not replace a malware scanner. A public untrusted-upload rollout should define scanning/quarantine policy before broad access. No scanner, paid service or third-party asset import is installed. The implementation uses existing .NET 10 upload facilities; see [Microsoft upload guidance](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0).


## Voice messages

The text composer can record the user's own microphone, preview or discard it, then send a voice message with an optional caption. It never records SFU tracks or the room's mixed audio. Stop/cancel/navigation/account or access unmount end microphone capture. Hiding the document stops an active recording. Capture auto-stops at59seconds to leave encoding margin within the60-second server bound. Drafts stay in memory and survive an unconfirmed send; retry uses the same request ID and exact recording.

Recording requires runtime MediaRecorder support for `audio/webm;codecs=opus`. Chromium is verified with synthetic microphone input; other engines and physical devices require separate checks. Unsupported browsers keep text/file messaging available. Preview decodes this browser's recording and supplies finite WebM duration metadata. Server duration remains independently derived, rather than trusting that preview or the client's timer.

`POST .../channels/{channel}/voice-messages` accepts one recording up to2MiB (3MiB multipart envelope). It shares normal View/Send authorization, CSRF, the two-upload concurrency gate, private blob store/quota and message outbox/history/deletion cleanup. A bounded WebM validator requires one Opus audio track,48kHz,one/two channels, valid packet framing with at most64KiB per packet, consistent nondecreasing bounded timestamps, and a maximum60seconds from both packet durations and timestamps. Video, other codecs, lacing, arbitrary metadata, SeekHead/Cues/CRC and unsupported container layouts are rejected. It parses the supported recorder layout, not all Matroska files or the compressed audio waveform. The codec decoder remains the browser's responsibility; this adds no transcoder/runtime/service dependency.

Stored bytes receive deterministic finite duration metadata; database attachment fields distinguish File/Voice, content type and server duration. Existing file rows migrate to File without changing their blobs. Voice retry hashes cover original upload bytes, so altered metadata also conflicts even if normalization would produce equivalent stored audio. Normal file retry hashes remain backward-compatible.

Load voice message deliberately fetches currently authorized bytes; native audio controls provide playback/pause/volume/keyboard seeking. Close/removal/navigation revoke blob URLs and unmount cancels pending fetches. Download remains separate. Network/playback failures are recoverable. Direct API downloads still force octet-stream attachment with nosniff/CSP; only the validated audio type is used for the local player. Already fetched/heard media cannot be recalled.

Primary format references: [MediaRecorder capabilities](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static), [Matroska elements](https://www.matroska.org/technical/elements.html), [Opus framing RFC6716](https://www.rfc-editor.org/rfc/rfc6716.html). Synthetic browser checks exercise actual encoding, finite preview/player metadata and decoding, retries, cancellation and late-permission cleanup. They do not establish physical recording quality or cross-browser acceptance.
