# Gatherings

Active community members can organize a gathering from the community's **Gatherings** link. Choose a future date/time, an explicit time zone and 1–50 current invitees. Title, description, game and a subsequently uploaded cover are optional. An invitation does not change access to existing text or voice channels.

Each invited user has one response: Pending, Accepted, Declined or NeedsClarification. Clarification requires a comment. An organizer's reply or an ordinary discussion comment preserves responses. Only the invited account may respond for itself. The organizer and community members with ManageRoles can manage the gathering; organizer, active invitees and these moderators can view it. These rules apply to HTTP, images and live routing. Unavailable private resources return 404.

Leaving, kicking or banning retires an invitation. Rejoining the community does not restore it; the organizer must explicitly invite that account again. Retired participants disappear from the current participant list. Historical revisions retain decisions for context and remain restricted to current authorized viewers. An organizer requires active membership to access their own gathering.

## Plans and time

The page loads gathering data without exposing normal connection setup as a user action. Interrupted updates show a plain explanation; offline changes resume after connectivity returns. A final update interruption offers Check for new updates while HTTP polling continues. Schedule change history has its own section describing archived dates/games and participant responses.

Cover editing preserves a selected file after failure. A stale-version response refreshes the latest gathering and asks the user to confirm review of the current details/cover before retrying. This review control appears only for a version conflict; quota and other failures keep their own explanations. It does not upload an image or change a participant response by itself.

The server stores the original local time and explicit zone, together with a UTC instant. The browser shows both organizer time and viewer-local time. Nonexistent or ambiguous daylight-saving times are rejected; choose another time. Merely changing the displayed zone while preserving the instant does not ask users to confirm again. Time-zone rules use the host .NET/OS time-zone data; operators should keep it updated.

Changes to the start instant or game archive the old plan and responses, advance the plan revision and reset responses to Pending. Text and cover edits preserve decisions. Added invitees start Pending; removed invitees lose access. The UI requires review of a changed plan before another response. Stale revision requests return 409. Separate string-valued versions protect edits, covers and lifecycle changes against concurrent mutations.

Scheduled gatherings can be cancelled, or explicitly completed after their start. Cancellation and completion disable new edits, responses, preparation changes and discussion. Completion does not assert attendance. No recurring events, calendar synchronization, temporary channels, automatic matching or email/push reminders are implemented.

## Places and planning polls

An optional total-place limit1–51 includes one reserved place for the organizer. Existing active Accepted invitations migrate to confirmed places; no limit is configured initially. Accepting an invitation grants a free place when no reserve is waiting; otherwise the participant's response is Accepted with a separate Reserve place state. Decline/clarification or retired participation releases a place. Reserve is never promoted automatically, including when the limit grows; the organizer or a community moderator explicitly confirms a place or moves an accepted participant to reserve. Reducing the limit below existing confirmed places is rejected. The community writer lock serializes concurrent last-place requests. Shared version and actor/payload receipts protect management changes and retries. Existing limits of50 invitees remain.

Gatherings support up to10 time/game polls with2–6 distinct immutable options each. Time options store an explicit zone and resolved UTC instant; future/nonambiguous time validation matches the Gathering schedule. The organizer and current invitees can select any number of suitable options, including clearing their own vote. Per-voter versions prevent stale overwrites, while votes from different users do not compete for a shared expected version. Current authorized viewers see aggregate counts and only their own selected options. Removed participation clears its vote; reinvitation does not restore it. Polls do not grant channel access or introduce automatic matching.

Creating/closing a poll or applying an option is restricted to the organizer/moderator. Applying requires an explicit confirmation of the selected value and reviewed Gathering version, and can choose any option regardless of counts. An actual time/game change archives the current plan, advances its revision, resets responses/places/readiness/reminders and closes open polls. Applying the already-current value simply closes that poll without false reconfirmation or reset. Any other material plan change also closes old polls. Cancellation/completion closes polls and disables voting. These polls are within an existing gathering; there is no standalone discovery, automatic time matching or temporary channel creation.

Additional routes: `GET choices`, `PUT capacity`, `PUT seat`, `POST polls`, `PUT polls/{id}/vote` and `PUT polls/{id}/decision`. Reads and commands recheck current visibility and active membership; unavailable private gatherings/polls return404. Structure and vote limits are safeguards, not measured capacity claims.

## Preparation, personal reminders and calendar

Each gathering has up to30 active preparation items (160 plain-text characters each). The organizer or a community moderator adds, edits, assigns and removes items. Responsibility can be assigned only to the current organizer or a current invited community member. Only that assignee or a manager can change readiness. Edits use the gathering version and payload-bound command receipts; retries cannot restore removed items or overwrite a newer command. Up to300 historical item IDs per gathering are retained to prevent resurrection. Checklist updates refresh the shared view without sending every participant a notification. They preserve attendance responses.

Changing the start instant or game clears all readiness marks and disables personal reminders, requiring explicit review and opt-in again. A title, cover or equivalent time-zone display change preserves preparation. Changing item text or its assignee clears that item's readiness. Removing an invitation or community membership clears the former participant's assignments and reminder; rejoining or reinvitation does not restore them.

The organizer and invitees can independently enable an in-app reminder5,15,60 or1440 minutes before the start, or turn it off. Settings are private and have an independent string version. A due reminder is persisted as a personal Gathering notice under the existing community writer lock, with its delivery state and refresh hint in the same transaction. Repeated or concurrent worker attempts do not create duplicates. A late worker may deliver after the chosen time only while the gathering is still scheduled and has not started. Cancellation, completion, changed revision and retired participation prevent delivery; changing/disabling a reminder removes its previous notice. An immediate reminder is possible when the chosen lead time is already past. Existing Gatherings polling recovers persisted notices on return to the app. These are not browser push notifications, email or a guarantee to alert while the app is closed. `Gatherings__WorkerEnabled=false` also disables reminder delivery. The indexed due queue is processed in bounded batches of100 by the existing scoped hosted-worker loop; no extra service is required.

The detail page offers an explicit `.ics` download after explaining privacy and synchronization limits. Each authorized request exports only the title and UTC start, a stable event UID, current sequence and cancellation status. It includes no participant identities, description, game, discussion, checklist, private URL or authentication token. UTF-8 folding, CRLF and text escaping follow [RFC5545](https://www.rfc-editor.org/rfc/rfc5545). The file is a snapshot: import a fresh copy after changes or cancellation, and check the receiving calendar's import behavior. Exported files cannot be revoked. No external calendar permissions, OAuth, public feed or synchronization is introduced. Completed events retain their scheduled instant; no end time or attendance is inferred.

Additional authorized endpoints under each gathering: `GET preparation`, `PUT checklist/{itemId}`, `PUT reminder` and `GET calendar`. The preparation response contains the shared checklist and only the current user's reminder. Every export/read/mutation rechecks current gathering visibility. Calendar responses use no-store and nosniff. Shared version conflict requires reviewing the current checklist; personal reminder or plan conflict requires reviewing the latest reminder and plan. Draft text survives transport errors, and explicit retries retain their request ID.

## Persistence and delivery

The Gatherings module is part of the existing ASP.NET Core monolith. PostgreSQL stores gatherings, invitations, comments, archived revisions, command receipts, private image metadata, notices and a durable delivery queue. Mutation state, notices, audit and queued hints commit together under the community writer lock. Payload-bound request IDs acknowledge retries without replaying an old decision over later changes. Every replay rechecks current authorization.

`/api/v1/communities/{communityId}/gatherings` exposes creation/listing, candidates, detail/edit, own response, discussion, revisions, lifecycle, covers and personal notices. Lists are paged: 20 gatherings, 100 candidate members or notifications; detail includes up to 200 discussion comments. Limits are engineering safeguards, not measured capacity guarantees: 100 scheduled gatherings per community, 100 revisions per gathering, 50 invitees. Notice read marking is personal and idempotent.

The `/hubs/gatherings` SignalR hub requires a current authenticated session, active membership and same-origin browser connection. A subscription identifies one community. Delivery rechecks current session, membership and gathering visibility for each connection. Notifications contain only a community refresh hint, with no gathering ID, title, participant list or discussion. Recently removed invitees may receive this generic hint to clear their caches; their detail requests are denied. Revoked sessions/memberships terminate subscriptions. Failed publication retains the queue entry for retry. HTTP refetch on connection recovery and periodic polling recover current state and durable notices even if hints are lost. These are refresh hints, with no exactly-once or ordered transport claim.

The worker is enabled by default. `Gatherings__WorkerEnabled=false` disables it for controlled integration fixtures; HTTP persistence and recovery still work. The initial in-process routing registry supports one API process; scaling to multiple hosts requires a separate reviewed delivery design.

## Covers and verification

Covers use the existing private filesystem store and shared quota, outside the public web root. PNG/JPEG uploads are bounded to 2 MiB and 2048×2048; signature/header dimensions are checked, without full decoding or malware scanning. Stored bytes determine the response MIME type. Each download checks current authorization and the current cover pointer, and returns no-store/nosniff/sandbox headers. Replacement/removal retires the old image; the existing cleanup worker purges known retired files. Uncertain orphan files are retained under the existing attachment policy. See [private storage configuration](attachments.md).

English is the default; the Russian language switch also covers this workflow. Integration tests verify independent decisions, revision archives, duplicate/concurrent requests, authorization, membership revocation, private media, lifecycle/time-zone boundaries and failed delivery. Browser tests exercise live UI, lost acknowledgements, stale drafts, offline recovery, cover decoding, cancellation and post-ban removal at desktop/mobile sizes. Run the repository's `npm run check`, `npm run test:database` and `npm run test:e2e` using the prerequisites in [development instructions](development.md).
